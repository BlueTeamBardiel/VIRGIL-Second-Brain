# Application Logs

## What it is

In **Metroid**, Samus's suit logs every scan. Point the Scan Visor at a Space Pirate console, a Chozo lore tablet, or a dead Metroid husk, and the suit writes it down — what the thing is, what it did, when Samus saw it. Late in the game, when you're stuck on Tallon IV with no idea why a door won't open, you scroll back through those logs and find the entry that says "this door responds to Wave Beam frequencies" three sectors ago. The logs were always there. You just had to read them.

That's exactly what application logs do — every app on every host writes down what it did, and the SOC reads back through those entries when something goes sideways.

**Technical definition:** application logs are event records generated by software applications — web servers, databases, line-of-business apps, authentication services, custom code — documenting transactions, errors, warnings, security events, and state changes. They are distinct from OS-level logs (which record kernel, process, and system events) and security logs (which record auth and access control events from the OS perspective). On Linux, they typically live in `/var/log/` or an application-specific directory. On Windows, they live in Event Viewer under **Applications and Services Logs**, or in app-specific files (IIS in `C:\inetpub\logs\LogFiles\`, SQL Server in its own ERRORLOG).

## Why it matters

When the [[SIEM]] alert fires, application logs are usually where the truth lives. Network logs tell you a connection happened. EDR tells you a process ran. Application logs tell you *what the user actually did inside the app* — which row they pulled from the database, which admin function they invoked, which file they downloaded. That's the difference between "something looked weird" and "here is the exact transaction the attacker executed at 03:14:22 UTC."

CompTIA tests this under **Objective 1.2 — analyze indicators of potentially malicious activity** as one of the application-related indicators. The exam wants you to know: when you see anomalous app behavior, you go to the app logs. Not the firewall. Not Sysmon. The app's own log stream.

Career-wise, the L1 analyst who can read an Apache access log, an IIS log, a Windows Event Viewer application channel, and a JSON-structured app log without flinching is the L1 who gets promoted. Most analysts can read network traffic. Fewer can correlate it to what the application actually did.

## Key facts

### Where the logs live

| Platform | Default location | Notes |
|---|---|---|
| Linux (most apps) | `/var/log/` | syslog, auth.log, kern.log, app-specific subdirs |
| Linux (systemd) | `journalctl` | binary journal, query with `journalctl -u <service>` |
| Apache | `/var/log/apache2/` or `/var/log/httpd/` | access.log, error.log |
| Nginx | `/var/log/nginx/` | access.log, error.log |
| Windows OS apps | Event Viewer → Windows Logs → Application | EVTX format |
| Windows custom apps | Event Viewer → Applications and Services Logs | per-app channels |
| IIS | `C:\inetpub\logs\LogFiles\W3SVC<n>\` | W3C extended format |
| SQL Server | `…\MSSQL\Log\ERRORLOG` | also writes to Application event log |
| Containers | `docker logs <id>` / kubelet | stdout/stderr from PID 1 |
| Cloud apps | CloudWatch / Azure Monitor / GCP Logging | API-driven, not on a host disk |

### What an application log entry contains

A useful entry has: **timestamp** (UTC, ideally with timezone), **severity** (INFO/WARN/ERROR/CRITICAL), **source** (which module or class), **identity** (user, session, API token), **action** (what was attempted), **outcome** (success/failure), and **context** (request ID, transaction ID, source IP). If your app logs `"error"` and a timestamp and nothing else, you don't have logging — you have decoration.

### Indicators of malicious activity in app logs

This is the Objective 1.2 payload. What does "anomalous application activity" look like in the log stream:

- **Authentication anomalies** — bursts of failed logins followed by a success (credential stuffing landing), logins from impossible geographies, service accounts logging in interactively, logins outside business hours from accounts that never work nights
- **Privilege escalation** — `[[role-grant]]` events the change board didn't approve, admin function invocations by accounts that shouldn't have them, sudden appearance of new admin users (the "introduction of new accounts" indicator)
- **Unexpected output** — error stack traces that leak internal IPs, SQL syntax errors echoed back to the client (sign someone's poking at [[SQL injection]]), unusual response sizes from endpoints that normally return small payloads
- **Data exfiltration markers** — large `SELECT *` queries against PII tables, repeated paginated calls scraping an export endpoint, file download events for assets that normally have one viewer per quarter
- **Application-layer abuse** — `..%2f..%2f` path traversal in URI logs, `<script>` tags in form-submit logs, base64 blobs in user-agent fields, requests to `/wp-admin/` on apps that aren't WordPress
- **Service interruption signals** — error rate spikes, connection pool exhaustion, OutOfMemory entries, repeated process restarts
- **Unauthorized changes** — config change events written by non-deploy accounts, schema modifications outside the migration window, feature flag flips from unknown sources
- **Beaconing from the app itself** — outbound API calls on a fixed interval to a domain nobody in engineering recognizes (compromised library, supply-chain attack)

*The most damning entries are almost always boring. A successful login at 2:47am from an account that hasn't been used in six months is a single INFO-level line. It does not glow red.*

### Log formats you will read

- **W3C Extended** (IIS, some proxies) — space-delimited, header-defined fields
- **Apache Combined / Common** — the de facto access log format, parsable with awk in one line
- **Syslog (RFC 5424)** — priority, timestamp, host, app, structured data, message
- **JSON-structured** — modern apps; one event per line, parseable directly by [[SIEM]] without regex gymnastics
- **CEF / LEEF** — vendor-normalized formats designed for SIEM ingestion
- **EVTX** — Windows binary event log format, parseable with `wevtutil`, PowerShell `Get-WinEvent`, or EVTX-specific tools

### Best practices the SOC actually cares about

1. **Enable logging before you need it.** Logs you turned on after the incident don't help you investigate the incident. Default verbosity on most apps is too low — bump it for security-relevant events (auth, authz, data access, config change).
2. **Centralize.** Logs on the breached host are evidence the attacker can wipe. Logs shipped off-host in near-real-time to a [[SIEM]] or log aggregator (Splunk, Elastic, Graylog, Sentinel) are evidence the attacker has to compromise *another* system to destroy.
3. **Protect integrity.** Write-once storage, hash chains, append-only object stores. If an attacker with admin on the app server can `> /var/log/app.log` and erase the trail, your logging architecture has one foot in the grave.
4. **Synchronize time.** NTP everywhere. A 90-second clock skew between the web server, app server, and database makes timeline reconstruction painful and gives defense counsel something to attack in court.
5. **Retain to policy.** Most regulatory regimes want a year minimum; PCI DSS wants 90 days hot and a year total; some financial regs want seven. The IR team wants enough history to investigate slow-burn intrusions — dwell time medians sit around 10–20 days, but APTs camp for months.
6. **Parse and normalize at ingest.** Raw logs in a shared drive aren't queryable evidence. Logs parsed into a SIEM with consistent field names (`src_ip`, `user`, `action`) are.

### CompTIA exam traps

> **CompTIA exam trap:** application logs vs. security logs vs. system logs. CompTIA will hand you a scenario — "an analyst suspects a database admin abused their privileges to export customer records" — and ask which log source is most useful. The answer is **application logs** (the database's own audit log), not the OS security log. The OS log shows the admin logged in. The DB log shows the `SELECT` that pulled the records. Different question, different log.

> **CompTIA exam trap:** logs as evidence vs. logs as alerting. A log that exists but nobody reads is not detection — it's forensics. CompTIA distinguishes between *reactive* log review (after an incident, you read the logs) and *proactive* log analysis (the SIEM correlates logs in near-real-time and alerts). Both are valid, both are tested. Read the question carefully: "discovered" usually implies reactive; "alerted" implies proactive.

> **CompTIA exam trap:** chain of custody for log evidence. Log files acquired during IR are evidence. The acquisition has to be documented — who pulled them, when, hash before and after, where they're stored. A log file someone emailed to themselves isn't admissible. A log file pulled via documented procedure with a SHA-256 hash recorded is. CompTIA tests this under [[Chain of custody]].

> **CompTIA exam trap:** the difference between **logging enabled** and **logging useful**. An app can log every event at INFO level and still not record the authenticated username, the source IP, or the resource accessed. CompTIA asks scenario questions where the log "exists" but doesn't answer the investigative question. The right answer is usually "increase log verbosity / enable audit logging" rather than "buy more storage" or "deploy a new tool."

## SOC reality

- The 3am alert reads something like: *"Application: web-prod-04 — 47 failed login attempts in 90s from 185.220.x.x followed by 1 success — account: svc_reports."* L1's first move: pivot to the app log, pull the next 30 minutes of activity for `svc_reports`, find out what that service account just did. Then check whether `svc_reports` was supposed to be doing anything at all at that hour.

- The CISO's question is never "what did the firewall see?" It's "what did the attacker actually do *inside the application*, and what data did they touch?" That question gets answered from app logs, full stop. If you don't have them, you're guessing for the breach notification, and guessing is how lawyers get nervous.

- Never promise leadership "we have full logs" until you've confirmed it. Apps fail open on logging all the time — disk full, log shipper crashed three days ago, the developer "temporarily" disabled audit logging in March and forgot. *Verify the log stream is alive before you bet the incident on it.*

- Handoff: L1 confirms anomalous activity in app logs → L2 correlates with EDR and network telemetry → IR lead scopes the [[Blast radius]] → if PII or regulated data was accessed, legal and the privacy officer get the call within hours, not days. [[GDPR]] gives you 72.

- The boring truth: 80% of app log alerts are noise — a developer testing in prod, a misconfigured health check, a scanner the security team itself authorized last week and forgot to whitelist. The 20% that matter are the ones where the log entry is *plausible* — a real user, a real action, just at the wrong time or against the wrong resource. *Plausibility is the attacker's camouflage; that's why tuning matters more than volume.*
