# Dynamic & VLAN Trunking Protocol

## What it is

DTP modes pair up like matchmaking in a fighting game lobby — each side picks a preference (aggressive, passive, locked-in), and what actually happens depends on what *both* players brought. The port you configured isn't necessarily the port you get.

**Dynamic Trunking Protocol (DTP)** is Cisco's auto-negotiation mechanism that lets two adjacent switches figure out, without you holding their hand, whether the link between them should be an **access port** (carries one VLAN, for endpoints) or a **trunk port** (carries many VLANs tagged, for switch-to-switch). It does this by exchanging DTP frames across the link.

Two terms matter here:
- **Administrative mode** — what you typed in (`switchport mode ...`). Your stated preference.
- **Operational mode** — what the port actually became after DTP did its thing. The result of the match.

**VLAN Trunking Protocol (VTP)** is the sibling protocol that solves a different headache: instead of manually creating VLAN 50 on every switch in your network, one switch announces "VLAN 50 exists" and the rest sync up. It's a shared Google Doc for VLAN definitions — edit in one place, propagate everywhere.

## Why it matters

DTP left at default is the network equivalent of leaving your front door unlocked because the delivery guy *might* show up. An attacker plugging into a `dynamic-auto` port can send forged DTP frames pretending to be a `dynamic-desirable` switch — the port flips to trunk, and now they see traffic from **every VLAN**. This is the classic **switch spoofing / VLAN hopping** attack. Best practice on access ports: `switchport mode access` plus `switchport nonegotiate`.

VTP matters for the opposite reason: it's *too* helpful. A switch with a higher revision number wins. Plug in an old lab switch that happens to have revision 47 and an empty VLAN database, and it can wipe VLANs across your entire production domain. VTP has caused more outages than most malware. VTP version 3 added a primary-server model specifically because of this.

## Key facts

### DTP modes and outcomes

- **`switchport mode access`** — locked access port, no DTP frames sent. Like queueing solo and refusing to group up.
- **`switchport mode trunk`** — locked trunk, but still sends DTP frames.
- **`switchport mode dynamic-auto`** — passive, waits to be asked. The default on many Cisco switches.
- **`switchport mode dynamic-desirable`** — actively tries to form a trunk.
- **`switchport nonegotiate`** — mutes DTP entirely. Even if you later change the mode, no DTP frames go out. The "do not disturb" toggle.

Negotiation outcomes (think of it as a compatibility chart):

| Local | Neighbor | Result |
|---|---|---|
| access | anything | **access** |
| access | trunk | **invalid** (misconfig) |
| dynamic-auto | dynamic-auto | access |
| dynamic-auto | dynamic-desirable | trunk |
| dynamic-auto | trunk | trunk |
| dynamic-desirable | dynamic-desirable | trunk |
| dynamic-desirable | trunk | trunk |

Two passive sides (auto/auto) just stare at each other and stay access. At least one side has to want it.

### Trunk encapsulation

- Switches that support both **ISL** (Cisco legacy) and **802.1Q** will negotiate which to use.
- When negotiated, **ISL wins** as the default.
- `switchport trunk encapsulation dot1q` forces 802.1Q. On modern switches that only speak 802.1Q, this command doesn't even exist.

### VTP fundamentals

- VLAN database lives in **`vlan.dat`** on the switch's flash.
- A **VTP domain** is just a shared name. Switches with matching domain names sync; mismatched domains ignore each other.
- Default domain state is **NULL** — no name set, no VTP messages exchanged. A factory-fresh switch is silent until it hears or sets a domain.
- **Revision number** starts at 0 and increments on every VLAN change. Higher revision = newer = wins. This is the dangerous part.
- A switch only accepts updates from peers with a **higher revision number** in the same domain.

### VTP modes

- **Server** — can create, modify, delete VLANs. Forwards VTP messages. Syncs to higher revisions. The default mode.
- **Client** — read-only. Can't touch VLANs locally. Receives updates from servers and syncs to higher revisions. Like a Spotify free user — listens, can't edit the playlist.
- **Transparent** — does its own thing. Allows local VLAN changes, **forwards** VTP messages through but doesn't advertise its own. Revision number stays at **0**. The hermit mode.
- **Off** — disables VTP entirely. No VTP traffic generated. Local VLAN changes allowed. Only available in VTP v3 (and v2 if running off-capable IOS, but officially a v3 feature).

### VTP versions

| Version | VLAN range | Token Ring | Off mode | Primary server |
|---|---|---|---|---|
| **v1** | 1–1005 | No | No | No |
| **v2** | 1–1005 | Yes | No | No |
| **v3** | 1–4094 | Yes | Yes | Yes |

- v3 introduced **primary server** designation: only **one** switch per domain can be primary, and it's the sole authority allowed to create/modify/delete VLANs. This is the fix for the "rogue revision-number wipeout" disaster.
- v3's full 1–4094 range matches the actual 802.1Q VLAN ID space (extended VLANs included).

### Verification commands

- **`show interfaces switchport`** — administrative mode, operational mode, negotiation state. Where you confirm DTP did what you expected.
- **`show vlan brief`** — what VLANs the switch currently knows about.
- **`show vtp status`** — domain name, mode, version, revision number, VLAN count. The revision number here is the one that can ruin your week.
